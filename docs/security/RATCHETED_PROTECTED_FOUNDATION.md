# Ratcheted protected-content foundation

Status: source implementation under AI-assisted review; not wired into production intake. Protected runtime activation remains unconditionally blocked. This work does not complete the device-directory API, browser persistence/confirmation flows or deployment evidence, and is not an independent human audit or E2EESA certification.

## Exact candidate profiles and libraries

Pinned E2EESA development catalog: `8441335f359c6e446f9bfe8b959f9606ce341409` in Galinsky-Labs/End-To-End-Everywhere-Security-Architecture-Standard. These components implement the named candidate profiles, without a blanket conformance claim:

- `identity-account-root@0.1.0`: a separate client-held account root signs exact device enrollment/rotation/revocation events. Events bind identity/account, unique event ID, next sequence, exact predecessor-state hash and subject keys/generation. New signing-key possession is checked. Key IDs derive from actual public key bytes, so altered OpenPGP creation metadata cannot conceal key reuse. Server account/staff authority is insufficient.
- `verify-account-root@0.1.0`, `ALG-SHA256`: canonical two-party root subject, twelve five-digit groups and versioned QR payload. Only an explicit independent comparison creates a verification record. Changed roots invalidate it; an old matching digest cannot silently revive an invalidated record. Durable atomic invalidation remains a browser-integration requirement.
- `group-mls-rfc9420@0.1.0`: exact suite `0x0001 MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`, ts-mls **1.6.4** and its locked HPKE dependency. An explicit authenticated roster replaces the SDK's default accept-all credential service. Initial Welcome embeds the authenticated tree. Every reply has a fresh UpdatePath/epoch and binds the full application context in authenticated data and inside the encrypted message. Fixed thread membership prevents implicit additions/history sharing. Replays, unknown devices, wrong sender/record/epoch and changed rosters fail. Delivery cannot decrypt payloads.
- `attachment-chunked-aead@0.1.0`: fresh 256-bit key per file; 64 KiB chunks; random 32-bit prefix plus 64-bit big-endian counter; AES-256-GCM; bound chunk AAD; exact private manifest and whole-file SHA-256. Empty files have one authenticated zero-length chunk. Private filenames, sizes, hash and key must remain inside the authenticated MLS message. Current source attachment limit is 150,000 bytes and downloads must remain inert. The manifest digest matches the actual pinned upstream reference fixture.
- `secret-software-vault@0.1.0`: client-local passphrase protection uses **@noble/hashes 2.4.0** Argon2id v0x13, 64 MiB, three passes, then domain-separated HKDF-SHA256. Every vault generation has a fresh 256-bit content key, separately authenticated key wrapping and content, random GCM nonces, and exact identity/record/generation binding. A high-entropy master separates thread keys. No server escrow, private-key download or recovery-export API is provided.
- Selected history policy: `backup-none@0.1.0`, permitted by G28-023's explicit recovery/no-recovery scope. This is a source design choice; the browser must require clear acknowledgement before key creation. Losing all authorized endpoint state loses protected history. Knowing the local unlock passphrase or resetting email/account access cannot reconstruct deleted browser keys. External device enrollment and unverified identity replacement must be distinct, visible and signed as applicable. Do not present the prior OpenPGP recovery-file prototype as this policy or silently change an existing active user's recovery behavior; there are no production protected users.

The final endpoint/transport integration still needs the exact `client-web-hardened@0.1.0` obligations (including independent transparency monitoring) and `transport-tls13-classical@0.1.0` deployment evidence. An ordinary restrictive CSP does not defeat a malicious origin publisher. No unsupported post-quantum, hardware, non-exportability, perfect memory erasure or global revocation/recall claims are made.

## Reviewed SDK boundary and corrections

Base MLS permits omission of an UpdatePath for an add-only commit. E2EESA does not. `scripts/prepare-mls.mjs` checks upstream createCommit.js SHA-256 `2813d68a1457a55470bbb1f2d223e12aa61c69e18a177f920c51cbdccc4bb004` and changes only the path-selection condition to always generate a fresh path. It fails on any unknown source and is idempotent only for that exact patch. Runtime wrappers independently require the path. No cipher, signature, HPKE or ratchet primitive is reimplemented.

A second reviewed SDK behavior needs explicit handling: configuring zero historical epochs still retains them because the source uses `slice(-0)` and discards its computed consumed list. The wrapper wipes old receiver secret trees, sender-data and resumption secrets and drops all historical epochs before persistence. Skipped-generation retention is also zero, with a bounded maximum forward step. Ordinary application processing uses the SDK's authenticated unprotect function to verify the exact MLS sender, not just the application-supplied label.

Cryptographic processing clones mutable binary state before accepting a frame. A malformed message cannot destroy the original valid state. Only a fully authenticated successful transition retires the old in-memory state. Client integration must atomically persist state plus the exact pending cipher frame before sending; uncertain delivery must retry those immutable bytes. Browser locks/counter checks, single-use KeyPackage reservation/consumption and client-local ciphertext/history persistence are still required before activation. No private group state may be mirrored to the server under a static identity key, which would undermine forward secrecy.

Software zeroization is best effort: JavaScript runtimes, browser/OS copies, authorized local histories and user-held files prevent a promise of perfect memory or forensic erasure. Removed devices can retain previously learned plaintext/keys. Honest fresh epochs can heal an epoch-secret compromise; continuous endpoint or identity-authority compromise is outside that promise.

## Source evidence

Real cryptographic tests exercise MLS establishment/replies, exact authorized roster, explicit state serialization, sender/record/replay negatives, failed-ciphertext state preservation and retired epoch-key erasure. Attachment tests cover fresh keys, exact nonce construction, manifest reference digest, reorder/substitution/truncation/size limits and empty content. Vault tests exercise actual Argon2id/HKDF, key wrapping, wrong secrets, header substitution, stale generation and locking. Identity tests require root and device signatures, exact predecessor, distinct raw keys and irreversible retirement; verification tests enforce explicit out-of-band confirmation and persistent invalidation semantics. These are component tests, not completed browser/API integration or independent MLS interoperability evidence. Dependency audit reported zero vulnerabilities at review time.
