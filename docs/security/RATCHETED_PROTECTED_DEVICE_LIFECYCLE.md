# Root-authorized device lifecycle and controlled item export

Source follow-up to merged PR157, 10 November 2026. AI-assisted review and synthetic real-browser/API tests; no independent audit, activated protected service, selected active recovery policy or certification is claimed.

The root endpoint can sign an exact device revocation with the current generation and predecessor hash. The signed transition is persisted inside the encrypted vault before HTTP. A lost acknowledgement retries its original event/signature and clears the pending change only after authenticated history contains it. At least one active device remains; emergency administrative quarantine is a separate routing control and never fabricates a root signature. A stolen account root requires root replacement, not a claim that revoking one device repairs that compromise.

Rotation generates fresh device identity and MLS signing keys. The new encrypted pending vault is durable before publication. A root-holding endpoint can authorize its own rotation; a linked endpoint shares only a public device-signed request for independent fingerprint comparison and root signature. Unexpected request fields are rejected locally before transmission. A request that becomes stale while another device is authorized can be reissued against authenticated current history with a new event ID and signing proof, retaining the same locally held private keys. Explicit disposal warns that a lost acknowledgement may already have authorized the pending keys and deletes only that pending local vault. The original device ID advances to the next signed key generation. Original groups stay bound to their old generation, recipient approval is reset and new private one-time packages are required. Root verification survives a legitimate same-root device change; it does not authorize substituting new device keys into old groups.

Rotation atomically replaces the current encrypted vault and removes this browser's previous thread vaults only after the new generation is acknowledged. The vault generation advances across the change. A failed acknowledgement leaves an encrypted pending vault; the user unlocks that exact pending change with its new phrase. It does not silently overwrite accepted local keys or transfer old thread secrets. Explicit irreversible-loss acknowledgement and a typed confirmation are required in the UI.

After total root loss/compromise, a separately confirmed new root starts a fresh unverified identity. Previous roots are archived, their routing is quarantined and their old signed histories are retained for historical verification. The replacement receives no previous cryptographic trust, old thread keys or staff approval. Private old local thread vaults are deleted atomically only when the new root is acknowledged. A lost response resumes the exact new root; it never reactivates an archived root. An ordinary email/account reset cannot restore erased endpoint keys. Other devices' previously saved copies cannot be recalled.

Per-item export signs the exact record ID, current version, original device and generation. The server independently checks current scope, staff step-up where applicable and original-device authority, then audits the ciphertext export. The download is inert JSON/octet-stream containing original-recipient ciphertext and public proof history. It contains no private keys and is not advertised as recovery of erased MLS epoch keys or a plaintext backup. No bulk export or silent new-recipient export is introduced.

The real Chromium journey now exercises public linking, linked-device rotation authorized by a separate root browser, root-device rotation, lost-response signed revocation/retry, lost-response root replacement, original-generation access denial, approval clearing, root-verification preservation/invalidation, local thread-key deletion and a real UI-driven audited ciphertext download. It retains all PR157 message/attachment/concurrency/rollback/expiry/lock/egress checks. Production builds, complete CI and deployment observations are recorded separately.

A same-origin checker or a same-owner workflow is not proof of independent log/witness ownership. Owner-authorized AI review removes the external human audit prerequisite; it does not invent those actual controls or deployment observations. ## Logout and account closure regression

The prior integration accidentally called local key deletion from normal logout and global session revocation. Protected runtime was disabled and primary held zero protected identities, so no active protected user keys were claimed affected. This follow-up separates a metadata-only cross-tab lock from irreversible account-scoped deletion. Normal and global sign-out preserve encrypted vault bytes; explicit account closure deletes them after its server action succeeds, with legal-retention/key-loss guidance. A rejected administrator closure cannot delete local keys. The real complete portal Shell/Settings journey verifies all three flows, including returning with a new session and unchanged encrypted keys. A local erase failure after accepted account closure instructs the user to clear site storage rather than pretending the server account stayed open.
