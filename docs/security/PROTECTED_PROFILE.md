# Protected records: disabled static-encryption prototype

**Do not activate this prototype.** Review of the actual pinned E2EESA catalog and ADRs 0005/0006 found that network messaging requires a registered ratcheted pairwise or group protocol. Static OpenPGP has no forward secrecy or post-compromise recovery and does not satisfy that requirement. `loadConfig` now unconditionally rejects protected intake. The owner authorized AI review instead of external human review; that does not waive cryptographic requirements. The tests below establish prototype behavior, not completion of the required messaging adapter.

This is an application security profile, reviewed with AI-assisted source analysis and automated tests under the owner's authorization. It is not an E2EESA conformance artifact, certification, independent human audit, or claim that the whole application is end-to-end encrypted. The architecture inventory remains pinned to the development standard recorded in `source-flow-contract.json`.

## Protocol and boundaries

OpenPGP.js **6.3.2**, pinned with npm integrity in the lockfile and security contract, implements RFC 9580 version 6 Ed25519 signing/X25519 encryption keys and AES-256 authenticated message encryption. The library generates keys, protects private keys with a user passphrase, signs, encrypts, verifies and decrypts. Application code supplies deterministically sorted JSON for signatures; it implements no cipher or key agreement. The encrypted signed payload includes the exact context also signed outside the ciphertext: application profile, record UUID, monotonic message sequence, type, sender device, sorted exact recipient-device list and sender key generation. Server verification rejects substituted recipients, reused sequences, unknown/revoked devices, stale generations and invalid signatures. No plaintext submission field is accepted.

Keys are generated and unlocked only in the browser. A passphrase of at least 16 characters protects the downloaded recovery key. The private key/passphrase never reaches an API, email job, analytics event, SQL row or attachment scanner. Unlocked keys remain only in page memory and are cleared on Lock/navigation/reload; use a trustworthy device and keep the encrypted key and passphrase separately. There is no server escrow. Recovery imports the same key locally; email reset, staff grant, device enrollment and directory approval cannot decrypt old records or silently replace a revoked key. Losing both an authorized key and its backup loses decryption access.

Public-key enrollment requires a signature binding the account, device UUID and fingerprint. A security administrator with a current staff passkey separately approves an exact public fingerprint and bounded record-type scope, after independently verifying recipient identity and fingerprint. Approval requires the recipient's current corresponding staff role. Senders must enter the full fingerprint learned through a separate trusted channel. Decryption requires independently checked sender fingerprints as well. Merely reading a key from the hosted directory does not establish trust. The directory publishes account UUID, device label, public key/fingerprint, approval/type and generation; these are declared service-readable routing/authority metadata.

A record fixes its original recipient set, including the author's device. Replies cannot add devices or recipients. Every nonauthor recipient must still have current scoped approval; staff reads/replies and status actions require a fresh passkey. Staff role reassignment/revocation takes effect on subsequent requests. Security administrators can revoke a lost device without gaining its decryption key. Recovered revoked keys cannot be reapproved. Start a new record with explicitly reverified recipients when the old recipient set becomes unusable. Static OpenPGP encryption does **not** provide ratchet-based forward secrecy: possession of a recipient private key may expose that key's previously retained ciphertext. Revocation cannot erase retained plaintext, backups or downloaded copies.

## Attachments, export and lifecycle

Attachments up to 150 KB are inside the signed encrypted payload; their names, bytes and narrative remain unavailable to hosting and generic public-file scanners. The encrypted record and attachments share one transactional database row. No ephemeral Render filesystem or independent object generation is required. Recipients see no inline HTML/image/PDF preview. Downloads have an inert `.bin` suffix and explicit local quarantine/scanning guidance; users must assess untrusted files on approved recipient devices.

The API stores ciphertext and declared author/participant IDs, message count/type/status, retention date and legal-hold state. Metadata minimization is not anonymity. Receipt/status is available only to the record's participants. A single-record encrypted export requires current account authorization, CSRF, an unlocked original device signing the exact record/version/export context and an explicit confirmation. It commits a digest audit before returning ciphertext. No export expands cryptographic recipients or includes another user's records. Ordinary account export never contains decrypted protected content.

Records expire after 90 days unless held. Security administrators set/release holds with an evidence digest and fresh passkey; serialized purge deletes only expired unheld records and appends minimal tombstones. Account closure invokes a narrow database trigger that deletes unheld authored ciphertext and revokes devices; held ciphertext survives with nullable account foreign keys and pseudonymous historical IDs. Finance retention is separate. Public keys needed for historical signature verification remain available within authorized record exports. Legal-hold, deletion and key-generation rows are included in the same authenticated encrypted database backup as all encrypted attachments. Recipient recovery keys are separately user-held, never a database restoration secret. Before exposing any old restore, apply subsequent hold/deletion tombstones and offboarding; do not resurrect closed accounts or retired trust. Private backup store retention, generation schedules and production RPO/RTO require actual operator configuration/evidence.

## Threat review and verification

The trusted computing base includes the browser, OS, authenticator, deployed JavaScript/build/dependency chain, and independently verified identity channel. A malicious code publisher or compromised endpoint can steal plaintext or unlocked keys; encryption does not solve those threats. Protected views use the separate portal origin, restrictive CSP, no third-party scripts or telemetry, no rich-text HTML rendering, explicit origin/CSRF checks, bounded ciphertext/recipient/message sizes and rate limits. The cryptographic bundle loads only when opening the protected view. General hosting sees routing metadata and ciphertext, and cannot recover messages from an email or database key.

`tests/protected-crypto.test.mjs` exercises real library keys, exact-recipient encryption, signed inner/outer contexts, wrong keys/passphrases, altered records and plaintext-field rejection. The PostgreSQL HTTP integration tests cover privilege/CSRF, real JSONB serialization, duplicate sequences, recipient substitution, current-role removal, fresh MFA, export audit, legal holds/purge and irrevocable device revocation. `tests/browser/protected-records.mjs` generates/downloads/imports a real key in Chromium, encrypts an attachment, inspects SQL for plaintext canaries, decrypts locally, exports ciphertext, checks mobile overflow and rejects external egress/browser exceptions. Database recovery tests restore ciphertext, public-key generation and hold state, then decrypt only with the separately retained recipient key. These are application tests using OpenPGP.js; interoperability with a second implementation and independent expert review remain follow-up evidence, not fabricated results.

There is no production activation recipe for this prototype. A registered ratcheted adapter, authenticated device authority, client key/state lifecycle, revocation cutover, recovery policy and adversarial/interoperability evidence must replace it first. Actual staff recipients and deployment evidence are separately required. Until then, ordinary help accepts structured categories only and must never collect confidential narratives or attachments.
